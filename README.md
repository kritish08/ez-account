# ez-account

Double-entry accounting for a small Indian wholesale business: invoicing, inventory, payments, GST, and the ledger reports derived from them.

## Context

The first version was generated by an agent platform in January 2026 and put into daily use by a wholesaler. It billed customers correctly enough to keep using, and its books were wrong: inventory valued at zero on every balance sheet, product costs reset to zero when a name was edited, revenue credited twice when Publish was double-clicked. None of it raised an error, because a wrong number in a ledger is still a number, and every report downstream reads it without complaint. The commits since then are the record of finding those and deciding what to do about each one.

## Architecture, and why

### Money is a float, and one function rounds it

The obvious choice is `Decimal`, stored as `Decimal128`. I used `float` with a single rounding helper applied at every multiplication and boundary — `app/services/money.py:_money`, 28 call sites.

The reason was migration, not preference: the database already held thousands of float amounts written by the generated version, and converting them means a migration that has to be right the first time on a system already in daily use. Per-line values are rounded to 2 dp so running totals accumulate already-rounded values, which gives the same result as `Decimal` at rupee magnitudes with two decimal places.

What it costs: the guarantee is now empirical rather than structural. It holds for 2-dp INR at the magnitudes this business deals in; it is not a general claim, and nothing in the type system enforces that `_money` was called. The failure it was written for is specific — an invoice of many decimal-priced lines totalling `999.9999999…` and failing a `paid_amount >= total` check by a fraction of a paisa, so an invoice that was paid never marked itself paid.

### Two failure policies in the same file, chosen by what is being mutated

`app/routers/production.py` has a work order consume raw materials on start and produce finished goods on completion. Both write stock. They fail in opposite directions.

When consumption fails part-way, the order is left `IN_PROGRESS` with no rollback (`production.py:194-195`). When completion fails after the status flip, the status is rolled back so the user can retry (`production.py:250-252`).

The obvious approach is to compensate consistently — roll back on any failure. I did not, because the two operations are not the same kind of thing. Rolling back a completion re-enables a retry that produces the same finished goods once. Rolling back a consumption re-enables a retry that consumes the same physical sacks of raw material twice, and the warehouse has no compensating transaction. Where the loss is physical, stopping and asking a human is the cheaper error.

What it costs: a failed consume strands the order in `IN_PROGRESS` with no automatic recovery and no alert. Someone has to notice.

### An authorisation gate that fails open

`app/deps.py:is_admin:83-96` treats a user with no `role` field as an administrator.

Fail-closed is the correct default and I did not use it. Nothing in the application had ever written a `role` — only the provisioning scripts did — so every account in the live database was role-less. A gate that failed closed would have locked the owner out of his own backups at the moment of upgrade, which is a worse outcome than the one being defended against on a single-tenant deployment. An explicitly set non-admin role is honoured, so the gate becomes real as soon as a staff account exists, and `tests/test_backup_security.py` pins that a `role: "staff"` user gets 403 on both restore and factory reset.

What it costs: exactly what it looks like. Until someone creates a staff account, the admin gate admits everyone, and the guarantee rests on a deployment fact rather than on the code.

### The invariants that survive a bug are in the database — and the most important one isn't

`server.py:150-176` puts unique indexes on all five reference-number series and on `(product_id, serial_number)` and `(product_id, batch_number)`. Each carries a `partialFilterExpression` restricting it to documents where the field exists.

The obvious approach is an application-level check before insert, which is what the generated version did and which loses every race. The partial filter is the part worth explaining: a plain unique index fails to build on a collection whose older documents lack the field, so the usual outcome is that the index is abandoned and the check stays in Python. Restricting the index to documents that have the field lets the constraint exist immediately, without a backfill, on a database already in use.

What it costs: the constraint is forward-only. Documents written before it do not participate, so the database enforces uniqueness going forward and says nothing about what is already there. And the invariant that matters most — debits equal credits — cannot be expressed as an index at all. It is enforced by one test that walks a full trading day and asserts balance at eight checkpoints (`tests/test_financial.py:67`). That test would not have caught two of the three worst bugs I found: a purchase return crediting the wrong account and a voice-created invoice never recording its cash both kept debits equal to credits while putting the money in the wrong place.

### Revocation needs both a denylist and a version counter, because they answer different questions

Logout used to be client-side only: the browser dropped the token and the server kept honouring it for the remaining 24 hours. Two mechanisms now run in `app/deps.py:50-72`, and neither is sufficient alone.

A per-token `jti` denylist answers "sign this device out". `/auth/logout` inserts the presenting token's `jti`; other sessions are unaffected, which is what a user expects when they log out of a shared terminal. A denylist alone cannot express "sign out everything", because the server never enumerated the tokens it issued.

A per-user `token_version`, compared against a `tv` claim, answers "sign everything out" for a lost device. A counter alone cannot express single-device logout, because bumping it kills every session including the one asking.

The counter is a counter and not an "issued before this time" comparison for a reason that a test found: JWT `iat` has one-second resolution, so a timestamp check either admits tokens minted in the same second as the revocation or rejects the user's own immediate re-login. A monotonic integer has no such window. Tokens and users predating the change both read as version 0, so existing sessions kept working through the deploy.

The denylist is bounded by a TTL index on `expires_at` (`server.py:178-180`): a row only has to outlive the token it denies, so it deletes itself at exactly that moment and the collection cannot grow without limit.

What it costs: authentication is no longer stateless. Every authenticated request now performs two reads — the user document and the denylist lookup — and there is no cache in front of either.

### The factory-reset gate, and why four checks rather than one

`POST /api/system/reset` deletes every accounting collection. It was reachable with nothing but a valid session and no request body. It now requires, in `app/routers/settings.py:349-393`:

1. an authenticated session;
2. an administrator role, via `require_admin`;
3. the account password, re-entered and verified against the stored hash;
4. the phrase `DELETE ALL ACCOUNTING DATA`, matched exactly.

Each one defends a different attacker. The session defends against strangers. The role defends against a logged-in employee. The password re-entry defends against a stolen token, which is the realistic case — a token is exfiltrated, a password is not carried in the same place. The phrase defends against the owner himself, clicking through a dialog he has seen before.

On top of those, a one-hour per-user cooldown that a *failed* attempt also advances (`settings.py:372`, `:387`). That is the part with a cost: a wrong phrase or a wrong password burns the hour, so an owner who fat-fingers the confirmation waits sixty minutes to try again. Without it the phrase and the password would be guessable at full speed by anyone holding a token. The cooldown is in process memory, so it resets when the container restarts.

Reset keeps `users`, `settings`, `backup_logs`, `s3` and `counters`. Counters are exempt so reference numbers do not restart at 1 and collide with the numbers already inside existing backups.

### What the N+1 queries actually were

The dashboard issued `2N + M + K + 5` sequential queries: two per customer (`get_account_balance`, `get_customer_credit`), one per supplier, one aggregation per product over the whole `stock_movements` collection, plus per-period sums. At 200 customers, 50 suppliers and 100 products that is roughly 700 round trips for one page load. `/customers` did the same thing on a smaller scale, two aggregations per customer.

Both were rewritten to a fixed number of queries independent of N: one `$regex: ^customer:` aggregation over `ledger` for outstanding balances, one over suppliers, one `$group` on `credit_notes`, one `$group` on `stock_movements`, and `count_documents` for counts, joined in Python. `/customers` runs its three reads concurrently under `asyncio.gather` (`app/routers/customers.py:59-95`).

This was **counted, not measured**. The query-count reduction is a fact I can read off the code. The latency numbers in `FIXES.md` — "well under 500 ms", "was multi-second before" — appear under "Verify" headings and are acceptance criteria written for a human to check, not recorded measurements. There is no benchmark, no profile, and no timing artifact anywhere in this repository. I do not know what the endpoints cost in milliseconds before or after.

### Passkeys

WebAuthn registration and authentication are implemented server-side with Yubico's `fido2` (`Fido2Server`, `app/services/passkey.py:11-13`) and client-side in `frontend/src/lib/WebAuthnService.js`. Challenge state lives in `webauthn_states` under a TTL index with a five-minute window (`server.py:172`), so abandoned handshakes expire rather than accumulate.

The login flow is explicit and email-first: the user types an email, presses "Sign in with Passkey", the server returns the credential list for that email only, and `navigator.credentials.get()` runs (`frontend/src/pages/Login.js:44-58`).

**Conditional mediation is not implemented.** `window.PublicKeyCredential.isConditionalMediationAvailable` is referenced in the support check at `WebAuthnService.js:115-119`, but it is only tested for existence — never awaited — and `navigator.credentials.get()` at `WebAuthnService.js:99` is called without `mediation: "conditional"`. The email input carries `autoComplete="email"`, not `"username webauthn"`. There is no passkey autofill. Worse, requiring that symbol to exist makes the support check stricter than the feature needs: a browser that supports passkeys but not conditional UI hides the passkey button entirely.

## Running it

Four things must happen in order. Each has a distinct failure if skipped.

```bash
# 1. compose.yaml attaches to an external network (Traefik, in production).
docker network create n8n-singh_default

# 2. Mongo, as a replica set, on that network.
docker run -d --name ezaccount-cluster --network n8n-singh_default \
  quay.io/mongodb/mongodb-atlas-local:latest

# 3. Backend config.
cp .env.production.template backend/.env
```

In `backend/.env` set at least:

```
MONGO_URL=mongodb://ezaccount-cluster:27017/?directConnection=true
DB_NAME=ezaccount_local
JWT_SECRET=            # openssl rand -hex 32
MASTER_ENCRYPTION_KEY= # openssl rand -hex 32
CORS_ORIGINS=http://localhost:8080
```

Step 4 is `compose.override.yaml` in the repository root. It is gitignored because it is machine-specific, so a fresh clone has to create it — without it no ports are published to the host and the JS bundle is built against the production API origin:

```yaml
services:
  backend:
    environment:
      CORS_ORIGINS: "http://localhost:8080,http://localhost:3000"
    ports:
      - "8001:8001"
  frontend:
    build:
      args:
        REACT_APP_BACKEND_URL: "http://localhost:8001"
    ports:
      - "8080:80"
  backup:
    profiles: ["donotstart"]
```

Then:

```bash
docker compose up -d --build
curl http://localhost:8001/api/health     # {"status":"ok"}
```

The UI is at `http://localhost:8080`. The nginx container serves static files only and has no `/api` proxy, so the browser calls the backend on its own origin — which is why `CORS_ORIGINS` is mandatory and why `http://localhost:8080/api/health` returns the SPA shell rather than JSON. Use port 8001 for the API.

Tests run inside the backend image against the same replica set:

```bash
cd backend && ./run_tests.sh -q            # 137 passed
```

Why the order matters, with the errors:

- Skipping step 1: `network n8n-singh_default declared as external, but could not be found`. To avoid the external network entirely, delete the `networks:` blocks from `compose.yaml`.
- Skipping step 2, or starting Mongo outside that network: the backend logs `Name or service not known` for every index, its healthcheck fails, and `docker compose up` ends with `dependency failed to start: container ez-backend is unhealthy`. It fails slowly — see the missing client timeout below.
- Using a plain `mongo` image instead of `mongodb-atlas-local`: `record_payment` opens a multi-document transaction (`app/routers/payments.py:72`) and a single-node `mongod` rejects `start_transaction`. The Atlas-local image is a single-member replica set, which is also what production runs on.
- An unset `CORS_ORIGINS` stops the process at startup by design (`app/config.py:parse_cors_origins`).

Verified on this machine: `137 passed` against a container created fresh for the purpose, and `{"status":"ok"}` from `http://localhost:8001/api/health`.

## What's imperfect

**Real customer data is in the git history.** Commit `76e32a5` contains five photographed bill scans — handwritten ledger pages with customer names, dates and amounts. Four were untracked in `a37f901`; the fifth sat at `backend/backend/uploads/` and survived because the ignore rule read `backend/uploads/`. I untracked it and widened the rule, which removes it from the working tree and changes nothing about the history. Committed credentials — a MongoDB Atlas URI and an Azure OpenAI key — are in that same history across three files. Both need rotation and a `git filter-repo` pass before this repository is shared.

**No tenant isolation.** Records carry no owner field and queries are not scoped; roles are not a substitute. Two businesses on one deployment would merge. Documented at the point where it would be enforced, `app/deps.py:11-17`, rather than in a backlog.

**`/api/uploads` is an unauthenticated static mount** (`server.py:240-243`). Bill scans are served to anyone with the URL. The filenames are UUIDs, which makes them unguessable, not protected.

**Stock is recomputed from the beginning of time.** `app/services/stock.py:36-52` runs a `$group` over the entire `stock_movements` collection with no `$match` and no rollup, and the product list, the balance sheet, the dashboard and production start all call it. It is the first thing that will fall over as movement history grows, and there is no snapshot table to fall back on.

**No pagination anywhere.** 52 `to_list(None)` calls in the routers and no `.limit()` or `.skip()`. A business with 5,000 invoices sends 5,000 to the browser.

**The Mongo client has no timeouts.** `app/database.py:12` constructs `AsyncIOMotorClient(MONGO_URL)` with no `serverSelectionTimeoutMS`, no `connectTimeoutMS` and no pool sizing, so an unreachable database means a 30-second hang per request rather than a fast failure. This is how the container ends up "unhealthy" rather than "down".

**The transaction has no retry and carries a stale guard.** `app/routers/payments.py:72` opens a transaction manually rather than through `with_transaction`, so a `TransientTransactionError` surfaces as a 500 instead of being retried as MongoDB's own guidance requires. The compare-and-swap re-read at `payments.py:112-130` was written before the transaction wrapped it; inside a transaction a conflicting write aborts rather than returning `modified_count == 0`, so that recovery branch is close to unreachable and the comment at `payments.py:14` describes behaviour that no longer applies.

**PDF rendering blocks the event loop.** `reportlab` runs synchronously inside the request handler (`app/routers/invoices.py:602-614`) while `boto3` uploads are correctly moved off the loop with `asyncio.to_thread` (`app/routers/backup.py:126`). The same fix was applied in one place and not the other.

**The rate limiter is per-process** (`app/services/rate_limit.py:1-18`). One container today; running two would double every limit. The module says so, and names Redis as the trigger for change.

**Thirteen of fifteen table pages are still desktop tables on a phone.** `Invoices` and `Customers` were converted to card lists as the pattern; the rest were not.

**`bom.py` and `exports.py` have no tests, and there are no frontend tests at all.** The suite reflects where I had seen things break, not coverage.

**Create React App is end-of-life**, which is why `npm audit` reports build-time advisories with no fix path. I have not recounted them in this tree; an earlier audit said 62. A Vite migration is the remedy and has not been done.

## Stack

- Python 3.11, FastAPI 0.110, Motor 3.3 over MongoDB (replica set required)
- React 19, React Router 7, Tailwind 3.4, shadcn/ui, built with craco
- OpenAI Python SDK 2.54 (Responses API) for bill scanning and the voice assistant, optional at runtime
- `fido2` 1.2 for passkeys, `bcrypt` 4.1 for passwords, `python-jose` 3.5 for JWTs
- `reportlab` 4.4 for invoice PDFs, `boto3` 1.42 for S3 backups, AES-256-GCM (`cryptography`) for encryption at rest
- Docker Compose, nginx, GitHub Actions
